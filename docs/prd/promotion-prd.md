data flow

user -> front -> api call -> serverA.internal (RDBMS) -> serverB.internal(NoSQL) -> serverC.internal(RDBMS)

백엔드 시스템 설계 및 구현 과제 하기의 내용을 참고하여 위 도표에 있는 전체 서버를 구성해 주시면 됩니다. git repo에는 front 영역에 해당하는 코드는 필요 없습니다.
프론트 도메인과 서버 api 도메인이 다르다는 것을 표시하기 위한 내용입니다. 각 a,b,c 도메인에 해당하는 submodule이 하나의 git repo에 포함되어 있으면 됩니다. 다만, 각 서버는 독립적으로 기동하고, 배포되어야 합니다. 하기 평가 항목의 모든 내용을 구현해 주셔도 됩니다만, 시간이 부족할 경우 설명으로 대체 할 수 있습니다.
좀 더 자신 있는 영역에 포커스 해서 구현체를 제출하셔도 됩니다. 각 사용자가 요청 건 수에 제한이 있다는 의미를 서버측 제한된 리소스를 사용자 요청에 의 해 사용자에게 지급되는 것으로 이해 해 주셔도 됩니다.


1. 배경 및 목적 본 과제는 다수의 사용자가 동시에 대량의 데이터를 생성하는 환경에서, 시스템의 안정성, 데 이터 정합성, 그리고 효율적인 리소스 관리 능력을 평가하기 위함입니다. 응시자는 제한된 인프라 자원을 효율적으로 활용하여 최적의 아키텍처를 설계하고 이를 코 드로 증명해야 합니다.

2. 트래픽 시나리오 총 사용자: 1,000명 요청 부하: 각 사용자는 10초 이내에 100건의 요청을 발송 (평균 10,000 TPS 규모이나, 서 버 1대당 목표 처리량은 500~1,000 TPS) 데이터 형식: 10개의 필드를 가진 JSON 객체 프로토콜: HTTPS (보안 연결 및 오버헤드 고려)

3. 기술적 제약 및 인프라 사양 대규모 인프라를 구축하는 대신, 단일 노드의 한계를 극복하는 능력을 확인합니다. 서버 사양: 각 서비스(Server A, B, C)는 vCPU 1개, RAM 2GB 환경에서 구동된다고 가정 합니다.
   스택: Java / Spring Boot 권장
   데이터 저장소:
   Server A: RDBMS (사용자 요청 기록 및 유효성 검증)
   Server B: NoSQL (중간 데이터 가공 및 캐싱)
   Server C: RDBMS (최종 데이터 영구 저장)

4. 핵심 평가 항목 응시자는 다음 5가지 핵심 도전 과제에 대한 해결 방안을 코드와 문서로 제시해야 합니다.

① 대량 트래픽과 동시성 제어 Server A로 유입되는 동시 요청에 대해 데이터 유실 없이 RDBMS에 기록할 수 있는가? Connection Pool 관리 및 DB 락(Lock) 최소화 전략을 고민했는가?

② 분산 서비스 간 데이터 정합성 (Consistency) A → B → C로 이어지는 데이터 흐름에서 장애 발생 시 데이터 유실을 어떻게 방지할 것인 가? Idempotency(등가성): 동일 요청이 n회 반복될 경우 최종 목적지(Server C)의 데이터 중 복을 어떻게 막을 것인가?

③ 캐시 설계 및 Hot Spot 문제 해결 대량의 읽기/쓰기가 집중되는 구간에 캐시를 어떻게 적용했는가? 특정 데이터(Key)에 트래픽이 몰리는 Hot Spot(Cache Scorch) 현상을 어떻게 방지할 것인가?

④ 유량 조절 (Rate Limiting / Backpressure) Server A의 처리 능력을 초과하는 트래픽 유입 시, 시스템 전체의 붕괴(Cascading Failure)를 막기 위한 유량 제어 전략은 무엇인가?

⑤ 인프라 사이징 (Infrastructure Calculation) 본인이 구현한 서버가 단일 노드(1vCPU, 2GB) 에서 초당 몇 건(TPS)을 처리할 수 있는지 벤치마크 결과를 제시하십시오.

위 결과를 바탕으로, 실제 100,000명이 동시 접속하는 서비스를 운영하려면 총 몇 대의 서 버 인스턴스가 필요한지 논리적으로 계산하여 제출하십시오.
