콘서트 할인 쿠폰 발급 시스템을 설계하기 위해 기능적 요구사항과 비 기능적 요구사항을 파악한다.

요구사항을 파악시에는 쿠폰 발급시 워크 플로우를 따라가며 분석한다.

사용자는 특정 이벤트 페이지에서 해당 이벤트에 대한 쿠폰(리소스)을 발급을 요청한다.

## 기능적 요구사항

- 시스템 규모: 이벤트 별 할인 쿠폰 100 장, 이벤트는 100개 (사용자 1,000 명이 이벤트당 100 장을 다투므로 매진이 반드시 발생)
- 고객은 한명당 1개의 쿠폰만 발급 가능
- 사용도 할 수 있어야 함

## 비 기능적 요구사항

- 대량 트래픽과 동시성 제어가 되어야 한다
- 분산 서비스 환경에서 서비스간 정합성이 이루어져야한다
- 대량의 읽기 발생시 hot spot 문제를 해결해야한다
- server a 가 처리능력 초과시 전체 시스템 붕괴 방지해야한다
- 인프라 사이징에 대한 벤치마크 결과를 제시해야한다

## 규모 추정

위 요구사항에 대해 트래픽을 추정해본다

트래픽 시나리오:

- 사용자 1000명
- 10초 이내 10건 요청 발송 (초기 메모는 100건이었으나 아래 1000 TPS 목표와 맞지 않아 10건으로 정정. 한 사용자가 10초에 100건을 보내는 것은 현실적이지 않다)
- 1000 TPS 목표 (1000명 × 10건 / 10초)

위 내용은 각 a, b, c 서버의 역할과 데이터 흐름을 나타낸 것이다.

데이터의 흐름은 아래와 같다.

유저가 쿠폰을 발급 하는 데이터 흐름

사용자는 쿠폰 발급 요청을 하면 쿠폰 발급 요청 접수를 확인하게 되고

이후 일정 시간이 지나면 쿠폰 발급 완료를 내정보에서 볼 수 있다

1. A 서버
    1. 최초 유저 쿠폰 발급 요청 시도
    2. A 서버가 요청을 받아서 유저정보 인증 체크
    3. 유저 요청 기록 RDB, 요청당 커밋 batch 하지 않음
    4. B 서버 http 호출 with 서킷
2. B 서버
    1. 유저별 쿠폰 발급 신청 내역 체크 (유저당 1번만 발급 가능하므로)
    2. 유저별 쿠폰 발급 신청 내역 적재 Redis
    3. 쿠폰 발급 신청 kafka 이벤트 발행
3. C 서버
    1. kafka 컨슈머를 통해 쿠폰 발급 이벤트 컨슘
    2. 유저 쿠폰 발급 내역 체크
    3. 이벤트 유효성 체크
    4. 쿠폰 발급 처리
        1. 이때 coupon_type_inventory 의 재고를 event_id, coupon_type 컬럼 기준으로 차감한다
    5. 쿠폰 발급 성공/실패 이벤트 발행
    6. 이떄 유저 쿠폰 발급 내역 체크부터 쿠폰 발급 성공/실패 이벤트 발행까지 하나의 트랜잭션으로 묶여야 한다
4. B 서버
    1. kafka 컨슈머를 통해 쿠폰 상태 업데이트 이벤트 컨슘
        1. 이때 유량 제어를 통해 C 서버가 처리할 수 있는 양에 대해서만 이벤트를 컨슘한다
    2. 쿠폰 상태 업데이트 Redis
5. 스케줄러
    1. 스케줄러는 생성 상태의 이벤트 중 10초가 지났는지 아닌지에 대해 판단
    2. 만약 지났음에도 생성상태라면 해당 쿠폰에 대해서 C 서버에 RDB 질의
    3. 결과에 따라 쿠폰이 없다면 실패, 있다면 성공으로 업데이트 Redis

유저는 이벤트 정보 조회를 한다

1. B 서버
    1. 유저 이벤트 정보 조회
    2. 캐싱된 이벤트 정보를 반환한다
