# 인프라 사이징

> **자원 제약 표기 정정** — `docker-compose.yml` 의 `cpus: 1.0` 제한은 앱 컨테이너(server-a/b/c)에만,
> `cpus: 2.0` 은 Kafka 에만 걸려 있다. **MySQL 과 Redis 에는 CPU 제한이 없다.** 아래 서술의 "MySQL" 은
> 1 vCPU 로 제한된 컨테이너가 아니라 호스트 자원을 공유하는 컨테이너다.

> **2026-08-27 전면 재측정.** 이전 판의 사이징 근거였던 **"인스턴스당 median 499 RPS → 3 대"** 는 폐기한다.
> 두 가지가 잘못됐다. ① **500 TPS 를 제시한 부하에서 나온 값이라 상한이 아니다** — 499 는 "제시한 부하를
> 다 소화했다" 는 뜻이지 "더는 못 한다" 는 뜻이 아니었다. ② 그 측정 전체가 **`@Transactional` 이 외부 HTTP
> 호출을 감싸고 있던 코드 상태**(`ed27658`, PR #44 에서 제거)에서 이뤄져 커넥션 보유 시간이 부풀려져 있었다.
> 목표 부하와 같은 **1,000 TPS 로, 트랜잭션 경계를 정리한 코드에서** 다시 쟀다.
> 근거와 반증 과정은 [병목 분석 보고서](load-test-bottleneck-analysis.md),
> 원본 산출물은 `load-test/experiments/results/` 에 있다.

## 0. 요약

- **인스턴스당 측정 처리량**: 1,000 TPS × 60 초 부하에서 안정 구간 **977 req/s** (회차 977 / 988, 예열 직후 885).
  **실패율 0 %**, p95 37~40 ms.
- **이 값이 상한인 근거**: 같은 부하에서 server-a 의 CPU 가 max 0.95~1.00 — **1 코어를 다 쓴다.**
  같은 시각 MySQL 은 CPU 제한이 없는데도 한 코어의 1/3 만 쓴다. 제약은 **server-a 의 CPU** 다.
- **목표 부하**: **10 초에 1,000 명이 사용자당 10 건 → 평균 1,000 TPS**.
- **필요 인스턴스 수**: `목표 TPS / (인스턴스당 처리량 × 가용률)` = `1,000 / (977 × 0.7)` ≈ **2 대**.
- **사전 증설** — 이벤트 시작 30 분 전 2 대로 미리 scale-out + warmup 부하.

## 3. 인스턴스 수 산정 (Little's Law 변형)

### 3.1 산식

```
필요 인스턴스 수 = 목표 TPS ÷ (인스턴스당 처리량 × 가용률)
```

- **가용률 (utilization target)**: 70% — 100% 까지 쓰면 burst / queue 폭주 위험. p95 안정 영역에 헤드룸 30% 확보.

### 3.2 계산

```
필요 인스턴스 수 = 1,000 ÷ (977 × 0.7)
              = 1,000 ÷ 683.9
              = 1.46
              ≈ 2 대
```

> 인스턴스당 977 은 **1,000 TPS 부하를 실패 없이 소화한 값**이고, 그 지점에서 A 는 한 코어를 모두 쓰므로
> 상한도 그 근처다. 배포 직후 (예열 전 885) 를 기준으로 잡아도 `1,000 / (885 × 0.7) ≈ 2 대` 로 같다.

### 3.3 가용률을 70% 로 두는 이유

| 이유 | 설명 |
|---|---|
| **Burst 흡수** | 평균 1,000 TPS 라도 순간 피크는 그 이상. 100% 로 잡으면 spike 시 즉시 latency 악화 |
| **장애 인스턴스 흡수** | 한 대가 죽거나 GC pause 로 처리하지 못해도 나머지가 받음. 대수가 적을수록 한 대의 비중이 커서 헤드룸이 더 중요하다 |
| **큐의 비선형성 (측정으로 확인)** | ρ ≈ 1 인 run0 에서 같은 설정의 회차 간 p95 가 37 ms ↔ 782 ms 로 벌어졌다. 이론이 아니라 이 시스템에서 실제로 관측된 진폭이다 |
| **배포 / 롤링 업데이트 여유** | 일부 인스턴스가 재시작 중이어도 트래픽 처리 가능 |

## 4. 운영 전략

### 4.1 사전 증설 (Pre-warming)

이벤트 시작 30 분 전에 인스턴스를 2 대로 미리 scale-out + warmup 부하 (예: 50 RPS × 30 초) 를 흘려 JIT / 풀 워밍.

- ✅ **장점**:
  - 트래픽 spike 시점에 인스턴스가 모두 ready — JVM warmup / 커넥션 풀 초기화 / 캐시 워밍 완료.
    예열 전후 처리량 차이가 **885 → 977 (약 10 %)** 로 실제로 측정된다.
  - **HPA 의 scale-out 지연 (수십 초 ~ 수 분) 회피** — 트래픽이 몰린 뒤에 늘리면 시작 시점에 늦는다.
- ❌ **단점**:
  - 평시 / 이벤트 외 시간에도 비용 발생.
  - 이벤트 일정이 정해져 있을 때만 적합 — 비예측 트래픽엔 부적합.

## 5. 거부한 사이징 방식

### 거부 1 — 측정 없이 추정으로 사이징

"1 vCPU 면 대충 N TPS 하겠지" 식의 예상.

- ❌ **거부 이유**: 인스턴스당 실제 처리량은 도메인 / 트랜잭션 / 외부 의존성에 따라 천차만별. **측정이 권위**.

### 거부 2 — 단일 시점 측정만으로 결정

한 번 부하 테스트 결과만으로 사이징.

- ❌ **거부 이유**: 단일 측정은 환경 / 워밍업 / 외부 변수에 흔들린다. 본 보고서는 **예열 1 회를 버리고 3 회 측정**
  한 뒤 안정 구간을 baseline 으로 쓴다.

### 거부 3 — 가용률 / 헤드룸 미고려

`1,000 / 977 ≈ 1 대` 만 계산하고 끝.

- ❌ **거부 이유**: 100% 가용률 가정은 **장애 0 / GC 0 / spike 0** 인 이상적 환경에서만 성립한다.
  실제로 ρ ≈ 1 에서 p95 가 20 배까지 벌어지는 것을 측정했다 (§3.3).

### 거부 4 — 제시 부하의 달성치를 처리 한계로 읽기 ← **이전 판의 오류**

500 TPS 부하에서 499 RPS 가 나왔다는 이유로 "인스턴스당 500 TPS" 를 사이징 근거로 삼았다.

- ❌ **거부 이유**: 제시 부하를 다 소화했다는 것은 **하한**이지 상한이 아니다. 같은 인스턴스가 1,000 TPS 부하에서는
  977 을 낸다. **상한을 알려면 포화할 때까지 올려야 하고, 포화 여부는 자원 지표 (CPU 0.95~1.00) 로 확인해야 한다.**

### 거부 5 — 부하가 끝난 뒤의 스냅샷으로 병목·용량 판단 ← **이전 판의 오류**

`docker stats` 단일 스냅샷의 CPU 를 근거로 병목 위치를 지목했다.

- ❌ **거부 이유**: 부하 종료 시점의 값은 **부하가 끝났다는 증거**일 뿐이다. 같은 자리를 부하 **중** 시계열로 재면
  server-a 96 %, server-b 31.7 % 로 결론이 뒤집힌다 (§1.3).

## 7. 비동기 처리 측 사이징 — Server C

사용자 응답 경로 (A 진입) 와 발급 처리 경로 (C 의 Kafka consumer) 는 **속도가 다른 별개의 축**이다.
A 가 977 건/s 를 받는 동안 C 는 그보다 느리게 소비하고, 차이는 Kafka 파티션에 쌓인다.

### 7.1 측정 — 컨슈머 스레드 × 재고 행 개수 (run0 / run8 / run9 / run10)

| 조건 | 스레드 | 건당 처리 | **C 처리량** | 스레드 이용률 | C CPU max |
|---|---|---|---|---|---|
| 재고 행 1, 스레드 1 (현재 기본값) | 1 | 6.8 ms | **141 건/s** | 0.96 | 0.48 |
| 재고 행 1, 스레드 3 | 3 | 14.9 ms | 187 건/s | 0.93 | 0.75 |
| 재고 행 10, 스레드 1 | 1 | 7.0 ms | 135 건/s | 0.94 | 0.56 |
| 재고 행 10, 스레드 3 | 3 | 8.8 ms | **321 건/s** | 0.94 | 0.92 |

- **행이 하나면 스레드를 3 배로 늘려도 +33 % 뿐이다.** 건당 처리 시간이 2.2 배로 늘고, 늘어난 8 ms 는 전부
  `SELECT ... FOR UPDATE` 대기다 — hot row 경합의 직접 측정치.
- **행을 나누면 병렬화가 산다** (135 → 321 건/s). 즉 손실의 원인은 Kafka 병렬도가 아니라 **행 락**이다.
- **321 건/s 지점에서 C 의 CPU 가 0.92** — 다음 제약은 다시 1 코어다.
- **비용**: C 를 3 스레드로 올리면 같은 호스트의 A 가 밀린다 (988 → 781 건/s, −21 %). A 와 C 를 분리한
  환경이면 사라지는 비용이므로 로컬 단일 머신 측정의 한계로 명시한다.

### 7.2 C 의 처리량은 얼마여야 하는가

| 기준 | 필요 처리량 | 근거 |
|---|---|---|
| 회복 스케줄러가 미처리 구간에 닿지 않을 것 | **≥ 42 건/s** | 스케줄러 검사 속도 = batch 50 / cycle 약 1.2 초. C 가 이보다 느리면 스케줄러가 미처리 구간을 보고 재발행을 시작한다 |
| 명세 부하 (10,000 건) 를 30 초 안에 소진할 것 | **≥ 334 건/s** | 최악 가정 — 매진 단락이 하나도 없을 때 |
| **명세 조건의 실제 큐 유입** | **579 건, 1 초에 소진** | ADR-011 매진 캐시가 요청의 **82 %** 를 A 진입에서 끊는다 |

→ **명세 조건에서는 스레드 1 개 (141 건/s) 로 충분하다.** 최악 가정(334 건/s)이 필요해지는 것은 매진 캐시가
작동하지 않는 경우 (재고가 충분해 매진이 없는 대형 이벤트) 이며, 그때는 재고 행이 이벤트별로 나뉘므로
§7.1 의 "행 10 개 × 스레드 3 개 = 321 건/s" 구간에 들어간다.

## 8. Server A HikariCP pool 사이즈

### 8.1 1,000 TPS 기준 (현재 근거)

| pool | 처리량 | 503 | **커넥션 보유 시간 mean** | 획득 대기 mean | Little's Law 이론 용량 |
|---|---|---|---|---|---|
| **10 (적용값)** | **977 ~ 988 /s** | **0 건** | **4.8 ms** | 1.2 ms | `10 / 0.0048` = **2,083 /s** |
| 50 | 437 ~ 446 /s | 최대 20,319 건 | 38.6 ms | 134 ms | `50 / 0.0386` = 1,295 /s |

- **pool=10 의 이론 용량은 2,083/s 로 제시 부하의 2 배다. 풀은 제약이 아니었다.**
- **풀을 5 배로 키우자 보유 시간이 8 배로 늘고 처리량은 반토막**났다. 1 코어 위에서 동시 처리 수를 늘리면
  CPU 경합이 커지고, 그 지연을 Circuit Breaker 가 "B 장애" 로 오판해 503 을 대량 생산한다.
- 따라서 **pool=10 은 latency 튜닝값이 아니라 1 vCPU 를 보호하는 유입 제한 (admission control)** 이다.
  초과 요청은 CPU 를 쓰지 않고 풀 큐에서 대기한다.

| 인스턴스 | 적용값 | 근거 |
|---|---|---|
| **Server-A** | **10** | 1,000 TPS 에서 503 0 건 / 실패 0 %. 50 으로 키우면 붕괴 |
| **Server-C** | 10 | 어떤 부하에서도 peak active ≤ 3. 안전 헤드룸 포함 |

> **`@Transactional` 이 외부 호출을 감싸면 이 결론이 뒤집힌다.** 보유 시간이 4.8 → 14.6 ms 로 늘면 풀 이론
> 용량이 `10 / 0.0146` = 685/s 로 **CPU 천장(≈980/s) 아래로 내려가** 풀이 진짜 병목이 된다. 그 상태에서
> "풀이 부족하다" 는 진단은 맞지만 처방(풀 확대)은 틀린다 — 자세한 반증은
> [병목 분석 §4-1 · §4-2](load-test-bottleneck-analysis.md).

### 8.2 부록 — 500 TPS 스윕 (2026-05, 참고용)

`HIKARI_POOL_SIZE_A` 를 6 케이스로 바꿔 500 TPS × 10 초 × 10 회를 돌린 결과다.

| pool | RPS | p50 | p90 | p95 | dropped |
|---|---|---|---|---|---|
| 3 | 244 | 1,196 ms | 1,337 ms | 1,369 ms | 2,270 |
| **10** | 499 | 12 ms | 30 ms | 50 ms | 0 |
| 20 | 499 | 14 ms | 47 ms | 59 ms | 0 |
| 30 | 499 | 30 ms | 70 ms | 80 ms | 0 |
| 40 | 492 | 66 ms | 150 ms | 185 ms | 25 |
| 50 | 481 | 75 ms | 197 ms | 293 ms | 82 |

**이 표를 사이징 근거로 쓰지 않는 이유** — ① 부하(500 TPS)가 인스턴스 상한(≈980) 아래라 RPS 열은 "제시 부하를
다 소화했다" 는 뜻일 뿐 용량이 아니다. ② `@Transactional` 이 외부 호출을 감싼 코드 상태의 측정이라 보유 시간이
부풀려져 있다. 살아남는 것은 **"pool=3 은 그 자체로 ceiling", "키울수록 p95 가 나빠진다"** 는 방향성뿐이고,
방향성은 §8.1 의 1,000 TPS 측정과 일치한다.

> **HikariCP wiki 의 magic formula** (`Tn × (Cm − 1) + 1`) 는 본 시스템에서 `Cm = 1` 이라 결과가 1 이다.
> 데드락 방지 최소값일 뿐 throughput 사이징 가이드가 아니다 — **측정이 권위**.

## 9. 검증하지 못한 것

- **확장 후 재측정** — 단일 인스턴스 측정에서 대수를 산정했을 뿐, 2 대 구성에서 실제로 1,000 TPS 가 나오는지는
  확인하지 못했다.
- **1,000 TPS 를 넘는 부하** — 정확한 상한은 모른다. CPU 포화 관측으로 "≈980 근처" 라고 말할 수 있을 뿐이다.
- **Kafka 단일 broker** — broker 가 한 대이므로 이 구성이 실제 상한일 수 있다.
- **장시간 부하의 hot row 락 경합** — 측정은 10 초 / 60 초 단위였다.
- **로컬 단일 머신 측정** — 네트워크 지연과 다중 노드 조건이 없어 **절대값이 아니라 동일 환경 내 비교**로만 쓴다.
