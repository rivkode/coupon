# 시퀀스 다이어그램

> 본 문서는 시스템의 핵심 흐름 4개를 시퀀스 다이어그램으로 시각화. 각 흐름의 코드 위치와 ADR 링크를 함께 제공.

---

## 1. 발급 정상 (ISSUED)

가장 흔한 흐름. A→B 동기 (즉시 응답) + B→C 비동기 (Outbox + Kafka).

```mermaid
sequenceDiagram
    autonumber
    participant U as User
    participant A as Server A
    participant Ra as Redis (idem cache + rate bucket)
    participant Da as MySQL (server_a)
    participant B as Server B
    participant Rb as Redis (stock shards)
    participant Db as MySQL (server_b outbox)
    participant K as Kafka coupon.issued
    participant C as Server C
    participant Dc as MySQL (server_c coupon)

    U->>A: POST /api/v1/coupons/issue-requests<br/>X-User-Id, Idempotency-Key
    A->>Ra: Bucket4j tryConsume(userId)
    Ra-->>A: OK (토큰 남음)
    A->>Ra: GET idem:{userId}:{key}
    Ra-->>A: nil (cache miss — 첫 요청)
    A->>Da: INSERT issue_request (status=RECEIVED)
    A->>B: POST /internal/v1/coupons/issue (sync, 200ms timeout, CB)

    B->>Rb: EVAL Lua (idem GET → HSETNX coupon:code → DECR shard → SET idem)
    Rb-->>B: ISSUED + couponCode
    B->>Db: INSERT coupon_issue_outbox<br/>(coupon_code, user_id, idem, payload, published=false)
    B-->>A: 200 ISSUED + couponCode

    A->>Da: UPDATE issue_request (status=SUCCEEDED, coupon_code=...)
    A->>Ra: SET idem:{userId}:{key} = response (2xx 만, TTL 24h)
    A-->>U: 200 OK + couponCode

    Note over A,U: 사용자 응답 끝 — 이하 비동기

    rect rgba(254,243,199,0.4)
        Note over Db,C: B → C 비동기 영속 (Outbox poller)
        Db->>B: poller fixed-delay 200ms (initial-delay 5000ms): SELECT FOR UPDATE SKIP LOCKED published=false
        B->>K: send(topic=coupon.issued, key=userId, value=payload, headers)
        K-->>B: ack
        B->>Db: UPDATE published=true, published_at=now
        K->>C: poll record
        C->>Dc: INSERT coupon (UNIQUE constraint check)
        Dc-->>C: OK
        C->>K: ack offset
    end
```

**핵심 포인트**:
- ① ~ ⑪ 까지는 사용자 응답 latency 안에 일어남. ⑫ ~ 이하는 비동기.
- A 는 Redis 캐시 GET (hit miss) → DB INSERT → B 호출 → DB UPDATE → 2xx 일 때만 캐시 SET 순서.
  GET 후 chain → SET 패턴이라 race 가능 — 의도적 단순화. 최종 차단은 Server C UNIQUE 가 권위.
- B 는 Lua atomic 으로 race 차단. Outbox INSERT 실패 시 보상 (다음 시퀀스).
- 의미적 exactly-once 는 Server C 의 UNIQUE 가 권위.

**관련 코드**:
- `server-a/.../api/IssueRequestController.java` + `IssueRequestService.java`
- `server-b/.../application/CouponIssueService.java` + `infrastructure/redis/RedisStockClient.java`
- `server-b/src/main/resources/redis/issue-coupon.lua`
- `server-b/.../application/OutboxPoller.java` + `infrastructure/kafka/KafkaCouponIssuedEventPublisher.java`
- `server-c/.../infrastructure/kafka/CouponConsumer.java` + `application/CouponIngestService.java`

**관련 ADR**: [ADR-001](../../CLAUDE.md), [ADR-002](../../CLAUDE.md), [ADR-003](../../CLAUDE.md)

## 2. 발급 보상 트랜잭션 (Outbox INSERT 실패)

Server B 가 Lua 차감 성공 후 / Outbox INSERT 실패 시. 보상 = Redis 차감 복구.

```mermaid
sequenceDiagram
    autonumber
    participant U as User
    participant A as Server A
    participant B as Server B
    participant Rb as Redis (stock shards + coupon hash)
    participant Db as MySQL (server_b outbox)

    U->>A: POST /coupons/issue-requests
    A->>B: POST /internal/v1/coupons/issue
    B->>Rb: EVAL Lua (DECR + 코드 생성)
    Rb-->>B: ISSUED + couponCode
    B->>Db: INSERT coupon_issue_outbox
    Note over Db: ✗ DataAccessException<br/>(transient DB error 또는 UNIQUE 충돌)

    rect rgba(254,202,202,0.4)
        Note over B,Rb: 보상 트랜잭션 (~10 줄 코드)
        B->>Rb: EVAL compensate.lua (INCRBY shard + DEL coupon:code:{code})
        Rb-->>B: OK
    end

    B-->>A: 503 IssueTemporarilyUnavailableException
    A-->>U: 503 + Retry-After: 5
```

**핵심 포인트**:
- 보상 코드는 ~10 줄 (catch + Lua INCR + 로그). "거창한 Saga Orchestrator 없이 Choreography 로 충분"의 시그널.
- 사용자에게 503 + Retry-After. idempotency 캐시는 503 저장 안 함 — 재시도 가능.
- B JVM 이 Lua 직후 / Outbox INSERT 직전 크래시 시는 보상 못 함 — **유령 재고**, [`../runbooks/failure-modes.md`](../runbooks/failure-modes.md) §1.2 참조.

**관련 코드**:
- `server-b/.../application/CouponIssueService.java` (try/catch 보상 분기)
- `server-b/src/main/resources/redis/compensate.lua`

**관련 ADR**: [`../decisions/outbox-mysql-vs-redis-streams.md`](../decisions/outbox-mysql-vs-redis-streams.md) §5

## 3. 발급 SOLD_OUT (자기 샤드 재고 0)

```mermaid
sequenceDiagram
    autonumber
    participant U as User
    participant A as Server A
    participant B as Server B
    participant Rb as Redis (stock shards)

    U->>A: POST /coupons/issue-requests<br/>X-User-Id=U_n
    A->>B: POST /internal/v1/coupons/issue
    B->>B: shard = hash(userId) % 10
    B->>Rb: EVAL Lua (DECR event:1:stock:{shard})
    Rb-->>B: -1 (재고 0, 차감 거부)

    Note over B,Rb: Lua 가 음수 방지 — DECR 결과 < 0 이면 INCR 후 SOLD_OUT 반환

    B-->>A: 200 SOLD_OUT (status=FAILED)
    A-->>U: 200 OK + status=FAILED

    Note over U,Rb: 다른 샤드에 재고가 남아있어도 사용자는 자기 샤드만 본다<br/>(자기 샤드 SOLD_OUT fallback 미구현 — README 트레이드오프)
```

**핵심 포인트**:
- HTTP 200 + body 의 `status=FAILED` — 200 은 호출 성공, FAILED 는 비즈니스 결과 (재고 소진).
- 사용자 hash 가 자기 샤드만 본다 — 다른 샤드 fallback 없음. 의도적 단순화 (CLAUDE.md §10 / README 트레이드오프).
- Hot Spot 회피 — 단일 키 (`event:1:stock`) 대신 10 샤드.

**관련 코드**:
- `server-b/src/main/resources/redis/issue-coupon.lua` (DECR 음수 방지)
- `server-b/.../infrastructure/redis/RedisKeys.java` (`shardId(userId, eventId)`)

**관련 ADR**: [ADR-003](../../CLAUDE.md)

## 4. 사용 (redeem) 동시성 race + 멱등 흡수

같은 coupon 을 같은 user 가 동시에 redeem 시도. 낙관적 락이 한 명만 통과.

```mermaid
sequenceDiagram
    autonumber
    participant T1 as Thread 1 (X-User-Id=U)
    participant T2 as Thread 2 (X-User-Id=U)
    participant T3 as Thread 3 (X-User-Id=U)
    participant C as Server C RedeemCouponService
    participant Dc as MySQL (server_c coupon)

    par 거의 동시 진입
        T1->>C: POST /coupons/CODE/redeem
    and
        T2->>C: POST /coupons/CODE/redeem
    and
        T3->>C: POST /coupons/CODE/redeem
    end

    C->>Dc: T1: SELECT version=N
    C->>Dc: T2: SELECT version=N
    C->>Dc: T3: SELECT version=N

    rect rgba(220,252,231,0.5)
        Note over C,Dc: T1 가 먼저 commit
        C->>Dc: T1: UPDATE coupon SET used_at=now, version=N+1 WHERE id=? AND version=N
        Dc-->>C: T1: 1 row affected
        C-->>T1: 200 + newlyRedeemed=true
    end

    rect rgba(254,202,202,0.4)
        Note over C,Dc: T2 / T3 의 commit 시도 — version 이 이미 N+1
        C->>Dc: T2: UPDATE ... WHERE version=N
        Dc-->>C: T2: 0 rows affected
        C-->>T2: OptimisticLockingFailureException → 409 RACE_RETRY
        C->>Dc: T3: UPDATE ... WHERE version=N
        Dc-->>C: T3: 0 rows affected
        C-->>T3: 409 RACE_RETRY
    end

    rect rgba(219,234,254,0.4)
        Note over T2,Dc: T2 클라이언트 재시도 — used 분기로 자연 흡수
        T2->>C: POST /coupons/CODE/redeem (다른 idempotency-key)
        C->>Dc: SELECT (used_at != null + same owner)
        C-->>T2: 200 + newlyRedeemed=false + 기존 redeemedAt
    end
```

**핵심 포인트**:
- `@Version` 자동 동작 — Hibernate 의 `WHERE version=?` 절이 affected rows=0 시 OptimisticLockingFailureException.
- 첫 commit (T1) 만 used_at 을 set. T2 / T3 의 commit 은 0 rows → exception → 409 RACE_RETRY.
- 클라이언트 재시도 시 service 의 `if (coupon.isUsed())` 분기가 200 + newlyRedeemed=false 로 흡수.
- 의미적 멱등 — 두 idem 분기 응답은 둘 다 DB ms 정밀도로 정확히 일치.

**관련 코드**:
- `server-c/.../application/RedeemCouponService.java` (분기 + 낙관락 propagate)
- `server-c/.../api/exception/GlobalExceptionHandler.java` (`OptimisticLockingFailureException` → 409)
- `server-c/.../domain/Coupon.java` (`@Version` + `redeem()` invariant)

**관련 ADR**: [ADR-007](../../CLAUDE.md), [`../decisions/redeem-idempotency-without-cache.md`](../decisions/redeem-idempotency-without-cache.md)
