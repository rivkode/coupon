# 아키텍처 개요

> 본 문서의 출처는 [`docs/rivkode_system_design.md`](../rivkode_system_design.md). 두 문서가 충돌하면 그쪽이 우선.

---

## 1. 시스템 다이어그램

```
[User] ──HTTPS──▶ [Server A] ──sync HTTP──▶ [Server B] ──Kafka(issue)──▶ [Server C]
                  진입/요청 로그              Redis 적재 / 즉시 응답         재고 차감 / 영구 저장
                       │                          │   ▲                       │
                    [MySQL-A]                  [Redis] │                   [MySQL-C]
                  issue_request               pending  │ Kafka(result)       event 마스터
                  (per-request commit)        user 신청 ◀─────────────────── coupon_type
                                              event cache                    coupon_type_inventory
                                              @Scheduled (10s)               user_coupon
                                                                             outbox_event
```

---

## 2. 핵심 명제

| # | 명제 | 의미 |
|---|---|---|
| 1 | **응답 모델 = 비동기** | A→B sync HTTP 이지만 B 는 Redis 적재 + Kafka publish 후 즉시 200 "접수 완료" 응답. 사용자는 결과를 폴링/내정보 조회로 확인 |
| 2 | **재고 권위 = C MySQL** | `coupon_type_inventory` row + `SELECT ... FOR UPDATE` 비관적 락. 발급은 Kafka consumer 내 트랜잭션이라 사용자 응답과 분리 |
| 3 | **멱등성 = (user_id, coupon_type_id) UNIQUE** | 1 인 1 장 제약 자체가 멱등성. Idempotency-Key 헤더 / 별도 캐시 불필요 |
| 4 | **Backpressure = Kafka consumer throttle** | B → C 의 `max.poll.records` / `concurrency` 로 1 vCPU MySQL-C 가 처리 가능한 양만 흘림 |
| 5 | **양방향 Kafka** | B → C: 발급 신청 / C → B: 발급 결과. 사용자 폴링은 B Redis 만 조회 |
| 6 | **보완 = B 의 @Scheduled** | 10 초 이상 pending 인 신청 → C 의 internal GET API 직접 조회 → 결과 반영. Kafka publish 실패/유실 방어 |

## 3. 데이터 흐름

### 3.1 정상 케이스 (발급 요청 → 발급 성공)

1. **User → A**: `POST /api/v1/coupons/issue-request`, 헤더 `X-User-Id`, body `{event_id, coupon_type_id}`
2. **A**: 헤더 인증 → `issue_request` per-request commit → B 호출 (Resilience4j Circuit Breaker)
3. **A → B (sync)**: `POST /internal/v1/coupons/issue`
4. **B**: Redis `EXISTS issue:pending:{user}:{type}` 로 중복 체크 → 없으면 `HSET` + `ZADD issue:pending:zset` → Kafka `coupon-issue-request` publish (acks=all, idempotent producer) → 즉시 200 "접수 완료" 응답
5. **A → User**: 즉시 200 "접수 완료" 응답
6. **C** (Kafka consumer): `coupon-issue-request` consume → 1 트랜잭션:
   - `user_coupon (user_id, coupon_type_id)` 존재 여부 (UNIQUE 위반 시 idempotent)
   - `event` 유효성 (started_at ≤ now ≤ ended_at)
   - `coupon_type_inventory.available_count` 비관적 락 차감
   - `user_coupon` INSERT (status = SUCCESS, code = generated)
   - `outbox_event` INSERT (event_type = ISSUE_RESULT)
   - 커밋
7. **C** (Outbox poller): `outbox_event` → Kafka `coupon-issue-result` publish
8. **B** (Kafka consumer): `coupon-issue-result` consume → Redis `HSET issue:pending:{user}:{type} status SUCCESS code <code>` → `ZREM issue:pending:zset {user}:{type}`
9. **User → A → B**: 폴링 또는 내정보 조회 → B 의 Redis 에서 결과 반환

### 3.2 매진 케이스

6 의 비관적 락 단계에서 `available_count = 0` → `user_coupon` INSERT (status = SOLD_OUT, code = null) → outbox INSERT
이후 흐름 동일. 사용자 폴링 시 SOLD_OUT 결과 확인.

### 3.3 Kafka 유실/지연 보완 케이스

- B 가 step 4 에서 Kafka publish 실패: producer 재시도(`retries`) 후 최종 실패 시 Redis 에 pending 만 남음
- B 의 `@Scheduled` (1 초 주기): `ZRANGEBYSCORE issue:pending:zset 0 (now - 10s)` → 10 초 초과 pending 추출
- 각 pending 에 대해: C 의 `GET /internal/v1/users/{userId}/coupons/{couponTypeId}` 호출 → 존재하면 SUCCESS, 없으면 FAIL 로 Redis 갱신
- C 의 UNIQUE constraint 가 중복 publish 를 방어 (재시도해도 1 건만 발급)

## 4. 서비스별 책임 요약

| 서비스 | 데이터 | 핵심 로직 |
|---|---|---|
| **Server A** | MySQL `issue_request` | 헤더 인증 → 요청 로그 commit → B 호출 (Circuit Breaker) |
| **Server B** | Redis (pending Hash + ZSet, event cache) | 중복 체크 + 적재 + Kafka publish + 즉시 응답 / Kafka result consume → Redis 갱신 / `@Scheduled` 보완 / event GET 캐시 |
| **Server C** | MySQL `event`, `coupon_type`, `coupon_type_inventory`, `user_coupon`, `outbox_event` | Kafka consumer + 1 트랜잭션 (비관적 락 차감 + UNIQUE) + Outbox poller + Redeem API |

---

## 5. Kafka 토픽

| 토픽 | producer | consumer | 페이로드 |
|---|---|---|---|
| `coupon-issue-request` | Server B | Server C | `{request_id, user_id, event_id, coupon_type_id, requested_at}` |
| `coupon-issue-result` | Server C (via Outbox poller) | Server B | `{request_id, user_id, coupon_type_id, status, code, processed_at}` |

- 두 토픽 모두 partition key = `user_id` (같은 user 의 이벤트는 순서 보장)
- C 의 consumer 는 `concurrency = 1~2`, `max.poll.records = 10~50` (1 vCPU MySQL 의 비관적 락 처리량 보호)
- B 의 result consumer 는 Redis 단순 SET 이라 동일 throttle 필요는 없으나, 실패 격리를 위해 별도 listener container

## 6. 5 축 평가 항목 매핑

| # | 항목 | 핵심 기법 | 코드/문서 |
|---|---|---|---|
| ① | 대량 트래픽 + 동시성 | A 진입 단순화 + per-request commit / C 의 1 트랜잭션 비관적 락 | `server-a/IssueRequestService`, `server-c/CouponIssueProcessor` |
| ② | 분산 정합성 + 멱등성 | Saga(choreography) + Outbox + UNIQUE | `server-c/OutboxPoller`, UNIQUE `(user_id, coupon_type_id)` |
| ③ | 캐시 + Hot Spot | Redis pending 적재 + Event Cache-Aside | `server-b/RedisIssueRequestStore`, `EventCacheService` |
| ④ | Rate Limit / Backpressure | Kafka consumer throttle + Resilience4j Circuit Breaker | `server-c/KafkaConfig`, `server-a/RestClientCouponIssuingClient` |
| ⑤ | 인프라 사이징 | k6 부하 + Little's Law | `load-test/scenarios/`, `docs/reports/sizing.md` (작성 예정) |
