# 설계 결정 + 트레이드오프 — 코드 따라가기 투어

> **목적**: Day 1 ~ Day 4 동안 만든 시스템을 **설계 결정 + 트레이드오프 + 코드 위치** 의 세 축으로 종합한 학습 / 검토 가이드.
> ADR 인덱스 / 측정 보고서가 "결과" 라면, 본 문서는 **"왜 그렇게 결정했고 어떤 trade-off 를 받아들였나"** 의 narrative.
> 새 세션이나 코드 review 시 이 문서를 따라가면 30분 안에 시스템의 설계 의도를 따라잡을 수 있다.

---

## 0. 어떻게 읽는가

각 섹션 (Decision N) 은 5 부분 구조:

| 부분 | 내용 |
|---|---|
| **Problem** | 어떤 문제를 풀어야 했나 |
| **Options** | 어떤 옵션이 있었나 |
| **Choice** | 무엇을 선택했나 |
| **Trade-off** | 어떤 비용을 받아들였나 |
| **Code** | 코드 위치 (`file_path:line`) |

후반부에 **"의도된 미적용 (Trade-off summary)"** + **"평가 시그널"** 섹션.

## Part 1. 진입점 (Server A)

### Decision 1 — 사용자당 Rate Limit (Bucket4j Lettuce backed) {#d1}

**Problem**: 사용자 abuse (한 사용자가 1초에 100건 이상 던지기) 를 어떻게 방어할 것인가?

**Options**:
- (a) in-process token bucket (단일 인스턴스 정합) — 다중 인스턴스 시 정합 깨짐
- (b) Redis 기반 distributed bucket — Redis 의존성 추가, 다중 인스턴스 정합
- (c) downstream (server-b) 에 위임 — server-a 가 무방비 → 부적합

**Choice**: **(b) Bucket4j + Redis (Lettuce backend)**. 사용자당 capacity=10, refill=10/1s.

**Trade-off**:
- ✅ 다중 server-a 인스턴스 정합 — 같은 사용자의 토큰이 인스턴스 간 공유
- ⚠️ Redis 의존성 — 본 과제는 Redis 가 필수 인프라이므로 비용 작음
- ⚠️ Bucket4j 가 user-scoped 만 보호 → **system-wide admission control 부재** (Bulkhead 로 별도 해결, [Decision 14](#d14))

**Code**:
- `server-a/src/main/java/com/promotion/servera/api/filter/RateLimitFilter.java` — Servlet Filter 진입점
- `server-a/src/main/java/com/promotion/servera/infrastructure/ratelimit/UserRateLimiter.java` — Bucket4j proxy
- `server-a/src/main/java/com/promotion/servera/infrastructure/config/Bucket4jConfig.java` — Lettuce + Redis bucket factory
- `server-a/src/main/resources/application.yml` line ~76 — `app.rate-limit.user.capacity=10`

**연관 ADR**: CLAUDE.md ADR-005 / 보고서 §3.2 (RATE_LIMITED=0 의 의미)

### Decision 2 — Idempotency 3 단계 보호 (Redis 1차 + DB UNIQUE × 2) {#d2}

**Problem**: 같은 사용자의 같은 `Idempotency-Key` 재요청 시 결과를 **단일 발급** 으로 보장하면서, 사용자에게는 **즉시 응답** 을 줄 것.

**Options**:
- (a) Redis 캐시 only — Redis 손실 시 보호 깨짐
- (b) DB UNIQUE only — 매 요청 DB round-trip → 성능 영향
- (c) Redis 1차 (성능) + DB UNIQUE 2차 (정합) — 빠르고 안전
- (d) global UNIQUE (idem 단독) vs user-scoped UNIQUE (`(user_id, idem)`)

**Choice**:
- (c) **Redis 1차 + DB UNIQUE 2차** — 3 단계 (server-a Redis + server-b Redis + server-c DB UNIQUE)
- (d) **user-scoped UNIQUE** — `(user_id, idempotency_key)` 로 다른 user 가 우연히 같은 UUID 시 격리

**Trade-off**:
- ✅ 정상 흐름은 Redis hit 으로 sub-ms 응답
- ✅ Redis miss + 동시 요청 시 DB UNIQUE 가 권위
- ⚠️ Redis cache 가 503 응답 캐싱 안 함 (PR #6 결정) — 일시 장애 후 재시도 시 정상 처리 가능
- ⚠️ user-scoped UNIQUE 로 변경하기 위해 PR #12 / PR #16 의 Flyway 마이그레이션 필요했음 (`V2_*_user_scoped_idem.sql`)

**Code**:
- `server-a/src/main/java/com/promotion/servera/api/filter/IdempotencyFilter.java` — 1차 캐시 hit/miss
- `server-a/src/main/java/com/promotion/servera/infrastructure/idempotency/RedisIdempotencyStore.java` — `idem:{userId}:{key}` GET/SET
- `server-a/src/main/java/com/promotion/servera/infrastructure/persistence/IssueRequestJpaEntity.java` — `(user_id, idempotency_key) UNIQUE`
- `server-c/src/main/resources/db/migration/V2__align_coupon_idempotency_user_scoped.sql` — server-c UNIQUE 정합화

**연관 ADR**: CLAUDE.md ADR-004 / `decisions/server-b-user-scoped-idempotency-cache.md`

### Decision 3 — A→B 동기 호출 + Resilience4j Circuit Breaker {#d3}

**Problem**: 선착순 쿠폰의 발급 결과를 **사용자에게 즉시** 줘야 하는데, server-b 가 일시 지연 / 장애 시 server-a 의 thread 가 모두 묶이면 시스템 전체 다운.

**Options**:
- (a) 전체 비동기 + 폴링 — 사용자 F5 연타 → 트래픽 폭증 + UX 깨짐
- (b) A↔B sync + B→C async (하이브리드) — 즉시 응답 + 영구 저장은 분리
- (c) 메시지 큐 기반 진입 — UX 깨짐 ([Q5 의 Kafka 백프레셔 해석 A](../reports/01.load-test-results.md#75-kafka-백프레셔--두-해석의-선택))

**Choice**: **(b) A↔B sync (200ms timeout) + B→C async (Outbox + Kafka)**. Resilience4j CB (sliding-window=20, failure-rate=50%, slow-call=200ms, OPEN 시 5s wait) 로 보호.

**Trade-off**:
- ✅ 사용자에게 즉시 결과 (선착순 UX 보존)
- ⚠️ server-a thread 가 server-b 응답까지 묶임 — CB + 200ms timeout 으로 차단
- ⚠️ CB OPEN 시 사용자 503 + Retry-After — 사용자에게 "거부" 가 아닌 "재시도" 신호
- 측정 검증: spike 시나리오에서 CB_503 86% 흡수 ([보고서 §3.4](../reports/01.load-test-results.md))

**Code**:
- `server-a/src/main/java/com/promotion/servera/infrastructure/client/RestClientCouponIssuingClient.java` — `@CircuitBreaker(name="couponIssuing", fallbackMethod="fallback")`
- `server-a/src/main/resources/application.yml` line ~97 — `resilience4j.circuitbreaker.instances.couponIssuing`

**연관 ADR**: CLAUDE.md ADR-001 / 보고서 §3.4 / `decisions/server-a-tuning-load-test-driven.md`

## Part 2. 비즈니스 로직 (Server B)

### Decision 4 — 재고 권위 = Redis Lua atomic {#d4}

**Problem**: 1만 사용자가 동시에 재고 1개를 가져갈 때 race condition 없이 정확히 stock 만큼 발급하기.

**Options**:
- (a) RDBMS row lock (`SELECT FOR UPDATE`) — 1 vCPU 환경에서 락 경합으로 처리량 폭락
- (b) Redis `GET` + 검사 + `SET` — atomic 아님, race 발생
- (c) Redis `DECR` + 음수 검사 — atomic 하지만 음수 발생 후 보상 필요
- (d) Redis Lua script — `DECR` + 음수 방지 + 코드 생성을 한 atomic 으로

**Choice**: **(d) Lua script**. EVAL 안에서 4 단계 수행:
1. idem cache hit → 같은 결과 반환
2. 쿠폰 코드 충돌 검사 (HSETNX)
3. atomic DECR + 음수 시 INCR + DEL hash 보상
4. idem cache 등록

**Trade-off**:
- ✅ Redis 단일 thread + Lua atomic = race condition 0
- ✅ DB row lock 기반 대비 처리량 ~수십 배
- ⚠️ Lua script 의 디버깅 / 유지보수 비용 (작은 script 라 영향 작음)
- ⚠️ Redis 단일 노드 장애 시 stock counter 위험 — RDB+AOF 정책 + 운영 진화 (Sentinel / Cluster)

**Code**:
- `server-b/src/main/resources/redis/issue-coupon.lua` — 4 단계 atomic
- `server-b/src/main/java/com/promotion/serverb/infrastructure/redis/RedisStockClient.java` — Lua EVAL 실행
- `server-b/src/main/java/com/promotion/serverb/infrastructure/redis/RedisKeys.java` — 키 컨벤션

**연관 ADR**: CLAUDE.md ADR-003 / `architecture/04.Data-Stores.md` §3.3

### Decision 5 — Hot Spot 회피 = 재고 10 샤드 + user hash routing {#d5}

**Problem**: 단일 키 (`event:{id}:stock`) 에 1만 사용자가 동시 DECR 시 Redis 단일 thread contention.

**Options**:
- (a) 단일 키 — Hot Spot 발생
- (b) N 샤드 + user hash 라우팅 — 사용자별 라우팅, 일부 샤드 SOLD_OUT 시 다른 샤드 fallback 안 함
- (c) request coalescing — 동일 사용자의 burst 합치기 (idem 으로 이미 보호)
- (d) 큐 기반 직렬 처리 — UX 깨짐

**Choice**: **(b) 10 샤드** — `event:{id}:stock:{0..9}`, `Math.floorMod(Long.hashCode(userId), 10)` 으로 라우팅.

**Trade-off**:
- ✅ Redis Hot Spot 완화 — 평균 1,000 DECR / 샤드
- ⚠️ **자기 샤드 SOLD_OUT 시 다른 샤드에 재고 남아 있어도 사용자는 SOLD_OUT 응답** — 의도된 단순화. README 트레이드오프 명시
- 운영 진화: fallback 샤드 탐색 로직 (1~2 샤드 추가 시도)

**Code**:
- `server-b/.../RedisStockClient.shardId(Long userId)` — `Math.floorMod(Long.hashCode(userId), 10)`
- `server-b/.../IssueCouponService.issue(...)` — 샤드 선택 → Lua EVAL
- `architecture/04.Data-Stores.md` §3.2

**연관 ADR**: CLAUDE.md ADR-003 + `scope-decisions.md` (자기 샤드 SOLD_OUT fallback 미구현)

### Decision 6 — Outbox 패턴 = MySQL outbox + 보상 트랜잭션 {#d6}

**Problem**: Redis (재고) 와 Kafka (발급 사건) 가 atomic 안 되는 환경에서, Lua atomic 차감 후 Kafka 발행 실패 시 어떻게 일관성 회복?

**Options**:
- (a) Redis Streams 기반 Outbox — Redis 안에서 모두 처리 가능, 단 Kafka 와의 통합이 복잡
- (b) **MySQL Outbox + 보상 트랜잭션** — 정합성 명시, 보상 5줄 코드
- (c) Debezium CDC — 정통 + 강력하지만 5일 일정 외
- (d) 보상 없이 503 — 일관성 회피

**Choice**: **(b) MySQL Outbox + 보상**. server-b 의 INSERT outbox 실패 시 Lua: `INCRBY shard + DEL coupon:code:{code}` 보상 → 503 응답.

**Trade-off**:
- ✅ 정합성 회피하지 않고 보상 5줄 코드로 명시 — "어려운 문제에 대한 자각" 평가 시그널
- ⚠️ JVM crash (Lua 차감 후 / Outbox INSERT 전) 시 유령 재고 발생 가능 — 본 과제 미해결, 운영 진화 (reconciliation job 또는 CDC)
- ⚠️ Outbox poller 의 polling overhead — 200ms fixed-delay (Day 4 측정에서 정량 검증)

**Code**:
- `server-b/src/main/java/com/promotion/serverb/application/IssueCouponService.java` — try/catch 보상 로직
- `server-b/src/main/java/com/promotion/serverb/domain/CouponIssueOutbox.java` — Outbox aggregate
- `server-b/src/main/resources/db/migration/V1__create_coupon_issue_outbox.sql`

**연관 ADR**: CLAUDE.md ADR-002 / `decisions/outbox-mysql-vs-redis-streams.md`

### Decision 7 — Outbox poller + Kafka producer (acks=all + idempotence) {#d7}

**Problem**: Outbox 행을 Kafka 로 어떻게 발행할 것인가? 다중 인스턴스 환경의 중복 발행 / 누락 어떻게 방지?

**Options**:
- (a) Worker thread pool (ExecutorService) — 5일 일정 외, 복잡
- (b) `@Scheduled fixedDelay` + SKIP LOCKED — 200ms cycle, 다중 인스턴스 안전
- (c) Kafka transactional producer (transactional.id) — broker 부담 + 본 과제 외
- (d) CDC (Debezium) — 운영 진화 영역

**Choice**: **(b) `@Scheduled(fixedDelay=200ms)` + `SELECT ... FOR UPDATE SKIP LOCKED`**. Producer `acks=all` + `enable.idempotence=true`.

**Trade-off**:
- ✅ at-least-once 발행 + Server C 의 DB UNIQUE 가 흡수 = **의미적 exactly-once**
- ✅ 다중 인스턴스에서 SKIP LOCKED 로 동일 행 중복 처리 방지
- ⚠️ poller cycle 200ms = 발급 후 Kafka 발행까지 평균 100ms 지연 — UX 영향 작음 (사용자 응답은 이미 끝남)
- ⚠️ broker 미회복 누적 시 outbox 행 backlog — Day 4 측정에서 정량 검증

**Code**:
- `server-b/src/main/java/com/promotion/serverb/application/OutboxPoller.java` — `@Scheduled` + 트랜잭션 분리 (SELECT → publish → markPublished)
- `server-b/src/main/resources/application.yml` line ~50 — `producer.acks=all`, `enable.idempotence=true`
- `architecture/04.Data-Stores.md` §4.2

**연관 ADR**: CLAUDE.md ADR-002 / `decisions/server-b-outbox-poller-kafka.md`

## Part 3. 영구 저장 (Server C)

### Decision 8 — Kafka consumer + DB UNIQUE 가 멱등성 권위 {#d8}

**Problem**: Producer 가 at-least-once 라 같은 메시지가 두 번 도착할 수 있음. Server C 의 영구 저장 무결성을 어떻게 보장?

**Options**:
- (a) Saga Orchestrator + 명시적 상태 관리 — 1 vCPU 환경에 부담
- (b) Choreography + DB UNIQUE 흡수 — 가벼움, UNIQUE constraint 가 권위
- (c) consumer 안에서 dedup (Redis SETNX) — 추가 인프라

**Choice**: **(b) Choreography + DB UNIQUE**. `(user_id, idempotency_key) UNIQUE` + `code UNIQUE`. 중복 메시지 시 `DataIntegrityViolationException` → catch + INFO 로깅 + ack.

**Trade-off**:
- ✅ Saga Orchestrator 없이 1 vCPU 친화 + 코드 5 줄로 정합성 흡수
- ✅ 의미적 exactly-once
- ⚠️ Poison pill (잘못된 JSON) 시 DLT 미구현 — `ack-and-skip` 로 흡수, 운영 진화 (DLT + alert + replay)
- ⚠️ DB transient error 시 retry 후 stop — DefaultErrorHandler default

**Code**:
- `server-c/src/main/java/com/promotion/serverc/application/CouponIssuedEventConsumer.java` — `@KafkaListener` + 멱등성 catch
- `server-c/src/main/java/com/promotion/serverc/infrastructure/persistence/CouponJpaEntity.java` — UNIQUE constraints
- `server-c/src/main/resources/db/migration/V2__align_coupon_idempotency_user_scoped.sql`

**연관 ADR**: CLAUDE.md ADR-002 / `runbooks/failure-modes.md` §1.6

### Decision 9 — Redeem = 낙관적 락 (`@Version`) + 도메인 자체 멱등 {#d9}

**Problem**: 한 쿠폰을 동시에 두 번 redeem 시도할 때 어떻게 단일 사용 보장? 같은 쿠폰을 사용자가 다른 idem 으로 재요청 시 재차감 vs 멱등 어떻게?

**Options**:
- (a) 비관적 락 (`SELECT FOR UPDATE`) — 락 경합으로 처리량 영향
- (b) **낙관적 락 (`@Version`)** + retry 안내 — 동시 redeem 은 흔치 않은 가정
- (c) idem 캐시 추가 (별도 redeem table) — 도메인 자체 멱등이라 불필요

**Choice**: **(b) 낙관적 락 + 도메인 자체 멱등**. `Coupon.redeem(now)` 가 `used_at == null` 일 때만 set, 두 번째 호출은 멱등 분기 (기존 `redeemedAt` 반환).

**Trade-off**:
- ✅ 비관 락 대비 처리량 우위 (1 vCPU 환경)
- ✅ 별도 idem 캐시 / 테이블 없이 도메인 객체 자체로 멱등
- ⚠️ 동시 redeem 시 두 번째 thread 는 `OptimisticLockingFailureException` → 409 RACE_RETRY → 재시도 시 멱등 분기
- ⚠️ 다른 user 가 redeem 시도 → 404 마스킹 (소유권 누설 방지) — README 트레이드오프

**Code**:
- `server-c/src/main/java/com/promotion/serverc/domain/Coupon.java` — `redeem(Instant now)` + `@Version` 필드
- `server-c/src/main/java/com/promotion/serverc/application/RedeemCouponService.java` — 멱등 분기 + 소유권 마스킹
- `RedeemCouponConcurrencyIT` — 5 thread 동시 redeem 검증

**연관 ADR**: CLAUDE.md ADR-007 / `decisions/redeem-idempotency-without-cache.md`

## Part 4. 인프라 / 관측성

### Decision 10 — 자원 제약 강제 = docker-compose `cpus=1.0` + `mem_limit=2g` {#d10}

**Problem**: 1 vCPU / 2 GB 가정의 부하 측정이 신뢰성을 가지려면 호스트의 무제한 자원을 어떻게 컨테이너 단위로 제한?

**Options**:
- (a) bootRun 직접 — 호스트 자원 무제한 사용 → 측정 신뢰성 X
- (b) docker-compose `cpus` + `mem_limit` — 컨테이너 단위 강제, JVM `-XX:+UseContainerSupport` 가 자동 인지
- (c) cgroup 직접 조작 — 운영 영역, 본 과제 외

**Choice**: **(b) docker-compose 단위 강제** (PR #19) + `MaxRAMPercentage=70` (heap ~1.4GB).

**Trade-off**:
- ✅ 측정 결과의 신뢰성 — Phase B/C 측정값이 실제 1 vCPU 환경 baseline
- ⚠️ Prometheus / Grafana / Kafka UI 는 측정 도구라 cpus 제약 없음 (호스트 자원 사용) — 측정 도구가 측정 대상의 자원을 빼앗으면 왜곡

**Code**:
- `docker-compose.yml` line ~83 — server-a/b/c 에 `cpus: 1.0`, `mem_limit: 2g`, `mem_reservation: 1g`
- `server-a/Dockerfile`, `server-b/Dockerfile`, `server-c/Dockerfile` — JVM `-XX:MaxRAMPercentage=70`

**연관**: 보고서 §1 측정 환경

### Decision 11 — Prometheus + Grafana provisioning (Phase A) {#d11}

### Decision 13 — batch insert (5층 방어 + 명시적 트레이드오프) {#d13}

**Problem**: server-a 의 `IssueRequestService` 가 매 요청마다 tx1 (RECEIVED) + tx2 (마감) 2 commit. Phase B 측정에서 HikariCP pending 188 — pool exhaustion 의 주범.

**Options**:
- (a) JdbcTemplate batch insert + in-memory queue + scheduler flush
- (b) `@Async` + 별도 thread pool — tx2 만 비동기, 마감 일관성 약화
- (c) INSERT only + 별도 update 잡 — race 위험

**Choice**: **(a) in-memory ArrayBlockingQueue (capacity=1,000) + 200ms scheduler flush + 5층 방어**.

**5층 방어** (Day 4 PR #22, 사용자 질의 응답으로 명시):
1. **Bounded queue** (capacity=1,000) — 무한 증가 차단
2. **동기 INSERT fallback** — 큐 가득 시 그 요청만 즉시 동기 INSERT (graceful degradation)
3. **Graceful shutdown** — `@PreDestroy` 에서 큐 drain (iteration limit + 20s deadline)
4. **Heap watermark 모니터링** — 80% 도달 시 rejecting 모드 + 강제 flush
5. **(운영 진화) Persistent queue** — Chronicle / Kafka audit topic, 본 과제 미적용

**Trade-off** (보고서 §5.1.3):
- ✅ Phase C v2 측정으로 효과 입증: HikariCP pending 188 → 1, p95 4.06s → 0.83s
- ⚠️ **JVM 비정상 종료 (kill -9 / OOM) 시 in-flight audit 손실** (~수백 건). 쿠폰 자체 정합성은 server-c UNIQUE 권위 → 영향 없음
- ⚠️ RECEIVED 중간 상태 DB 미저장 — 사용자 GET `/issue-requests/{id}` 가 audit 손실 시 404 (드물게)
- 명시적 인지 — 운영 환경 (compliance critical) 진입 시 Persistent queue 도입

**Code**:
- `server-a/.../infrastructure/batch/BatchProperties.java` — `app.batch.*` ConfigurationProperties + watermark invariant
- `server-a/.../infrastructure/batch/IssueRequestBatchQueue.java` — 방어선 1, 4 + Counter / Gauge metrics
- `server-a/.../infrastructure/batch/IssueRequestBatchFlusher.java` — `@Scheduled(fixedDelay=200ms)` + JdbcTemplate.batchUpdate + `@PreDestroy` graceful drain
- `server-a/.../infrastructure/batch/HeapMonitor.java` — 방어선 4 (high 80% / low 70%)
- `server-a/.../application/IssueRequestService.java` — `tryEnqueue` + 동기 fallback (방어선 2)

**연관 ADR**: `decisions/server-a-tuning-load-test-driven.md` §6.2 / 보고서 §5.1, §9

### Decision 14 — 가상 스레드 (Java 21) — Tomcat 한계 폐기 {#d14a}

**Problem**: Phase B 측정에서 Tomcat busy=200 (default max 도달). thread pool 한계가 시스템 한계.

**Options**:
- (a) Tomcat thread max 200 → 500 증설 — 메모리 비용 (~1GB stack)
- (b) **가상 스레드 enable** (Spring Boot 3.5 + Java 21) — 1 줄 변경, carrier thread 가 다중화
- (c) 별도 reactive stack (WebFlux) — 본 과제의 동기 모델 전체 재작성

**Choice**: **(b) `spring.threads.virtual.enabled=true`** (server-a/b/c 모두).

**Trade-off**:
- ✅ Tomcat platform thread 한계 200 폐기 — carrier thread (1 vCPU = ~수개) 가 가상 스레드 다중화
- ✅ 메모리 비용 거의 무료 (~수 KB / 가상 스레드 vs ~2 MB / platform thread)
- ⚠️ synchronized block / native code = pinning 위험 — Spring Web + JDBC + HikariCP 는 가상 스레드 친화 (검증됨)
- ⚠️ Phase C 측정에서 결과적 안전성 입증 (OTHER_ERROR=0) — 운영 진입 시 `-Djdk.tracePinnedThreads=full` 정밀 검증 권장

**Code**:
- `server-a/src/main/resources/application.yml` line ~5 — `spring.threads.virtual.enabled=true`
- 동일 line server-b/c 의 `application.yml`

**연관**: 보고서 §7.4 / `decisions/server-a-tuning-load-test-driven.md` §6.2

### Decision 14 — Resilience4j Bulkhead admission control {#d14}

**Problem**: Bucket4j 는 사용자당 보호 만. 100 user × 10 req/s = 1,000 TPS 합법 트래픽이 그대로 통과해 자기 자원 (HikariCP / Tomcat) 소진 — system-wide admission control 부재.

**Options**:
- (a) Tomcat default queue 만 — 거부 시 사용자에게 의미 있는 응답 없음 (TCP reset)
- (b) **Resilience4j Bulkhead semaphore** — `max-concurrent=50, max-wait=0ms`, 큐 없이 즉시 거부 + Retry-After
- (c) Servlet Filter 의 명시적 큐 + 상한 — 두 단계 큐 (Tomcat + 명시적) 디버깅 복잡

**Choice**: **(b) Bulkhead semaphore**. Controller 의 `@Bulkhead(name="issueRequestBulkhead")`. `BulkheadFullException` → `GlobalExceptionHandler` → 503 ADMISSION_CONTROL + Retry-After.

**Trade-off**:
- ✅ ADR-005 의 "큐 가득 차면 503" 정합화 — system-wide admission control 충족
- ✅ Phase C v2 측정에서 CB_503 27% → 83% — 보호 메커니즘 적극 발동
- ⚠️ 큐 없음 (max-wait=0) → burst 흡수 불가 — 단, CB 가 downstream 보호와 결합해 사용자에게 명확한 신호 (Retry-After). 운영 분산 환경에서는 503 비율 자연 감소
- ⚠️ 50 = 헤드룸 30% 안전 영역. 1 vCPU 가 안전하게 처리 가능한 동시성

**Code**:
- `server-a/.../api/IssueRequestController.java` — `@Bulkhead(name="issueRequestBulkhead")`
- `server-a/.../api/exception/GlobalExceptionHandler.java` — `BulkheadFullException` → 503
- `server-a/src/main/resources/application.yml` line ~115 — `resilience4j.bulkhead.instances.issueRequestBulkhead`

**연관 ADR**: CLAUDE.md ADR-005 (system-wide admission control 정합화) / 보고서 §5.2

### Decision 15 — HikariCP pool 10 유지 (트레이드오프 회귀) {#d15}

**Problem**: Phase B 측정에서 pool 10 의 active=10 + pending=188. Phase C 에서 50 으로 증설했으나, batch insert 도입 후 pool 사이즈의 가치 재검토.

**Options**:
- (a) Pool 50 — burst 흡수 헤드룸, MySQL slot 150 거의 한계
- (b) **Pool 10** — batch insert 가 critical path 의 connection 점유 0 → 평균 ~6 connection 사용으로 충분
- (c) Pool 30 — 중간

**Choice**: **(b) Pool 10 회귀** (Phase C v2 는 50 으로 측정했으나 트레이드오프 분석 후 10 으로).

**Trade-off**:
- ✅ batch insert 효과는 동일 (Phase C v2 의 핵심 효과는 batch 가 만든 것, pool 사이즈 부차적)
- ✅ MySQL slot 여유 (3 × 10 = 30 vs default 151)
- ✅ 1 vCPU 환경의 context switch 비용 절약
- ⚠️ Burst 시 fallback rate 폭증 가능성 — Bulkhead admission control 이 시스템 capacity 를 먼저 제한하므로 pool 까지 도달 안 함

**Code**:
- `server-a/src/main/resources/application.yml` line ~14 — `maximum-pool-size: ${HIKARI_POOL_SIZE:10}`
- 동일 line server-b/c

**연관**: 보고서 §5.3.2 (회귀 사유 + 비교 표)
