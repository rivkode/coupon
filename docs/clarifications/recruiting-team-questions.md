|---|---|

## 1. 채용팀에 문의한 3가지 질문

### 1.1 트래픽 시나리오의 의미가 시스템 전체 부하인지, 단일 인스턴스가 처리해야 하는 부하인지

요구사항에 다음 두 숫자가 함께 명시되어 있다.

- 사용자 1,000명 / 사용자당 10초 내 100건 / 평균 **10,000 TPS**
- 인스턴스당 목표 **500 ~ 1,000 TPS**

두 숫자의 관계가 다음 어느 의미인지 확인 요청.

| 옵션 | 해석 | 본 과제의 설계 영향 |
|---|---|---|
| **(a)** | 10,000 TPS 는 시스템 전체 부하 — 인스턴스당 500 ~ 1,000 TPS 처리량 기준 10 ~ 20 인스턴스 분산 처리 가정 | 1 인스턴스 baseline 측정 = budget 검증용 (~1,000 TPS). 사이징 = 분산 인스턴스 수 산출 |
| **(b)** | 10,000 TPS 가 단일 인스턴스가 받아야 하는 부하 — 1 vCPU / 2 GB 환경에서 부분 거부 / 보호 / 보상으로 안정 동작 시키는지 설계 자체가 평가 대상 | 1 인스턴스가 10x budget 트래픽을 어떻게 보호하면서 흡수하는지 — 백프레셔 / Rate Limit / CB 의 적정 동작 비율이 평가 |

답변에 따라:
- 부하 테스트 시나리오의 동시 사용자 수 (50~100 VU vs 1,000 VU)
- 보호 메커니즘의 적정 발동 비율 (CB 503 27% vs 83%)
- 구현 우선순위

가 달라진다.

### 1.2 "100,000명이 동시 접속하는 서비스" 의 정확한 의미

사이징 산출 항목의 "100,000명이 동시 접속하는 서비스를 운영하려면 총 몇 대의 서버 인스턴스가
필요한지 논리적으로 계산" 에서 "동시 접속" 의 정의 확인 요청.

| 옵션 | 해석 | 산출되는 인스턴스 수 |
|---|---|---|
| **(a)** | 100,000명 동시 사용자 — 요구사항의 트래픽 모델 (사용자당 10 req/sec) 그대로 확장 = 평균 **1,000,000 TPS** | 1,000 ~ 2,000 인스턴스 |
| **(b)** | 100,000 TPS 의 시스템 전체 처리량 — 1,000명 시나리오의 10배 | 100 ~ 200 인스턴스 |
| **(c)** | 100,000 RPS / 100,000 동시 TCP connection | 다른 지표 — connection 기반 사이징 |
| **(d)** | DAU 100,000명 — peak 시간대 일부 사용자만 활성 | 분산 트래픽 가정 — 5 ~ 50 인스턴스 |

답변에 따라 (a) 와 (b) 가 약 10배, (a) 와 (d) 가 약 100배 차이 — 사이징 보고서의 결론이 5대
~ 2,000대 사이를 오감.

### 1.3 "인프라 확장(Scaling) 계획 및 계산 근거" 의 형태

요구사항의 "총 몇 대의 서버 인스턴스가 필요한지 논리적으로 계산" + "계산 근거" 에서
기대되는 산출 형태가 어디까지인지 확인 요청.

| 옵션 | 해석 | 보고서 깊이 |
|---|---|---|
| **(a)** | 산수 — 목표 TPS / 인스턴스당 TPS = N 인스턴스 + 헤드룸 + 가정 명시 | 1 페이지 — 수치 표 + 식 |
| **(b)** | 산수 + 실측 근거 수치 — 인스턴스당 처리량을 직접 측정한 결과를 산출의 input 으로 사용 + 비선형 한계 (USL / context switching) 고려 | 측정 보고서 + 산출 식 |
| **(c)** | 산수 + 인프라 비용 추정 (인스턴스 / RDBMS / Redis / Kafka 별도 사이징) + 운영 진화 경로 | 종합 capacity planning 문서 |

답변에 따라 보고서의 양 / 깊이 / 보강 영역이 달라진다.

## 2. 메일 본문 (참조)

채용팀에 발송한 메일 원문 (원형 보존):

```
안녕하세요 담당자님, 이종훈 입니다.

과제 진행 중 요구사항 해석에 대해 다음 3가지를 확인하고 싶어 문의드립니다.


1. 트래픽 시나리오의 의미가 시스템 전체 부하인지, 단일 인스턴스가 처리해야 하는 부하인지

   요구사항에 "사용자 1,000명 / 사용자당 10초 내 100건 / 평균 10,000 TPS" 와
   "인스턴스당 목표 500 ~ 1,000 TPS" 가 함께 명시되어 있습니다. 두 숫자의 관계를
   어느 쪽으로 이해하면 좋을지 확인하고 싶습니다.

   (a) 10,000 TPS 는 시스템 전체 부하 — 인스턴스당 500 ~ 1,000 TPS 처리량을
       기준으로 10 ~ 20 인스턴스 분산 처리를 가정하는 시나리오인지
   (b) 10,000 TPS 가 단일 인스턴스가 받아야 하는 부하 — 1 vCPU / 2 GB 환경에서
       어떻게 부분 거부 / 보호 / 보상으로 안정 동작 시키는지의 설계 자체가
       평가 대상인지

   해석에 따라 부하 테스트의 동시 사용자 수, 보호 메커니즘의 적정 발동 비율,
   구현 우선순위가 달라져 의도를 알고 진행하고 싶습니다.


2. "100,000명이 동시 접속하는 서비스" 의 정확한 의미

   사이징 산출 항목의 "100,000명이 동시 접속하는 서비스를 운영하려면 총 몇 대의
   서버 인스턴스가 필요한지" 에서 "동시 접속" 이 어느 정의인지 궁금합니다.

   (a) 100,000명 동시 사용자 — 요구사항의 트래픽 모델 (사용자당 10 req/sec) 을
       그대로 확장 = 평균 1,000,000 TPS
   (b) 100,000 TPS 의 시스템 전체 처리량
   (c) 100,000 RPS / 100,000 동시 TCP connection
   (d) DAU 100,000명 — peak 시간대 일부 사용자만 활성

   정의를 알면 사이징 보고서의 결론을 정합하게 작성할 수 있을 것 같습니다.


3. "인프라 확장(Scaling) 계획 및 계산 근거" 의 형태

   요구사항의 "총 몇 대의 서버 인스턴스가 필요한지 논리적으로 계산" + "계산 근거"
   에서 기대되는 산출 형태가 어디까지인지 알고 싶습니다.

   (a) 산수 — 목표 TPS / 인스턴스당 TPS = N 인스턴스 + 헤드룸 + 가정 명시
   (b) 산수 + 실측 근거 수치 — 인스턴스당 처리량을 직접 측정한 결과를 산출의
       input 으로 사용 + 비선형 한계 (예: USL / context switching) 고려
   (c) 산수 + 인프라 비용 추정 (인스턴스 / RDBMS / Redis / Kafka 별도 사이징),
       운영 진화 경로

   보고서에 어느 깊이로 채우는 게 평가에 맞는지 알면 보강 영역을 적절하게 작성할
   수 있을 것 같습니다.


좋은 하루 보내세요.
감사합니다.
```

## 5. 본 문서의 위치 / 평가 시그널

본 과제는 5일 일정의 take-home 형식으로, 요구사항이 100% 명확하지는 않은 영역이 일부 있다.
본 문서는 다음 메시지를 평가자에게 보내는 역할을 한다.

1. **요구사항을 받아들인 후 모호한 영역을 식별** — 단순 추정으로 진행하지 않고 의도 확인
2. **각 모호함이 산출물에 미치는 영향을 정량적으로 분석** — 인스턴스 수 5대 vs 2,000대 차이
3. **답이 오기 전까지 명시적 가정 위에서 진행** — README / 보고서가 이 가정과 정합
4. **답이 오면 산출물을 갱신 가능한 구조** — 본 문서 §4 의 체크리스트가 추적

5일 일정 안에 모든 답을 받기는 어렵지만, 질문 자체가 "요구사항을 깊이 이해하고 진행했다" 의
시그널이 된다.
